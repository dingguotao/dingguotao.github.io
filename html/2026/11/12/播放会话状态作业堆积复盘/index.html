窗口聚合的 accumulator 是一个按视频维度组织的 Map：

WindowPlaySessionAgg.PlayAggAccum窗口状态结构
protected static class PlayAggAccum {
    private MapView<Tuple2<Long, String>, PlayItem> PLAY_MAP = new MapView<>();

    // key = (avid, from_spmid)，即一个视频 + 一个来源页面
    // value = PlayItem：clientTime + 完整 avbasicBody + Map<cid, playedTime>
}

每条记录进入 accumulate 后，按 (avid, from_spmid) 找到或新建对应条目，把 (cid, playedTime) 合并进去。同一 cid 只保留更大的播放时长，条目和 cid 都只增不减。窗口结束时整个 Map 序列化成 protobuf 输出。

状态的构成与写回方式

Flink 在每条记录处理完后把整个 accumulator 写回状态后端，并非只写增量。指标可以直接印证这一点：

window_aggs_readValueLength2.6 KB单次读取拿到一个 PlayItem
window_aggs_writeValueLength均值 27 KB，峰值 77 KB推测为整个 MapView，未确认

下面这组是推测数据，只用于描述膨胀可能的形态。按 readValueLength 的单次读取量折算（均值 8.99 KB，0.99 分位 2.6 KB），膨胀 subtask 的 60~73 KB 大致对应 8~28 个条目，取值取决于用哪个口径，两种口径本身互相矛盾。另一种同样成立的可能，是单个 PlayItem 内部的 playCids 或 avbasicBody 膨胀，与条目数无关。现有指标区分不了这两种情况。

可以直接观测到的旁证只有一条：窗口输出的 protobuf 平均 118 字节，约一条行为。无论膨胀来自条目数还是单个 PlayItem，这些内容大部分没有进入输出。

总状态最大的是 sub 84（32.91 MiB），但它的增量只有 52.7 KB；增量排前 7 的 subtask，总状态都排在中后段。膨胀发生在写入增量，不累积。

UDF 实现

线上 jar 为 online-pc-play-session-state.4a5d9d18633936c0eee14d7d4a5e4206db9adb71，反编译结果与 git tag v1.9.95 的源码一致。下面三段逻辑与状态膨胀直接相关，代码为节选，注释是本文补充。

WindowPlaySessionAgg.accumulate每条记录的合并入口
public void accumulate(
        PlayAggAccum acc, Timestamp metaTimestamp, String clientTimeStr,
        String avidStr, String cidStr, Integer playedTime,
        String from_spmid, @DataTypeHint("BYTES") byte[] avBasicRaw) {

    ReportUtils.count(rctx, "PC_PLAY_STATE", "input_num");
    RecsysAvbasicBody avbasicBody = factory.produce(new byte[0]);
    if (avBasicRaw == null) {
        ReportUtils.count(rctx, "PC_PLAY_STATE", "av_basic_null");
    } else if (avBasicRaw.length == 0) {
        ReportUtils.count(rctx, "PC_PLAY_STATE", "av_basic_empty");
    } else {
        try {
            avbasicBody = factory.produce(avBasicRaw);   // 完整的视频基础信息对象
        } catch (Exception e) {
            ReportUtils.count(rctx, "PC_PLAY_STATE", "av_basic_parse_error");
        }
    }

    long avid = 0, cid = 0, clientTime = 0;
    try {
        avid = Long.parseLong(avidStr);
        clientTime = Long.parseLong(clientTimeStr);
        cid = Long.parseLong(cidStr);
    } catch (Exception e) {
        ReportUtils.count(rctx, "PC_PLAY_STATE", "agg_parse_error");
        // 解析失败后三个值保持 0，方法继续执行
    }

    if (clientTime <= Constant.SAFE_TS) {
        return;
    }
    acc.addPlayCid(clientTime, avid, cid, playedTime, from_spmid, avbasicBody);
}
PlayItem.addPlayCid条目内只增不减
public void addPlayCid(long cid, int playedTime, long clientTime) {
    if (clientTime < this.clientTime) {
        this.clientTime = clientTime;
    }
    long lastPlayDur = playCids.getOrDefault(cid, 0);
    if (playedTime > lastPlayDur) {
        playCids.put(cid, playedTime);      // 只保留更大的播放时长，从不删除
    }
}

PLAY_MAP 的写入路径同样只有 contains、get、put，代码里没有 remove，也没有条目数或 cid 数的上限。状态完全依赖 Flink 的窗口生命周期回收。

窗口清理判定

processing time 窗口的触发和清理由 ProcessingTimeService 的 timer 驱动，不依赖 watermark，watermark 停滞不会让窗口不清理。反压时 timer 回调会在 mailbox 里排队，窗口状态会短期滞留，但不会无界累积。数据也支持这一点：如果 5 秒窗口不清理，40 分钟会累积 480 个窗口，状态量涨几百倍，SST 不可能只从 16.78 MB 增长到 17.37 MB。checkpoint 从 1.5 GB 涨到 2.46 GB 主要是 RocksDB 文件与 in-flight 数据，重启后回落到 1 GB。

重启也不能清掉大状态。19:34-19:44 期间异常 subtask 仍维持 56~67 KB，19:45 才回落。恢复的原因是那批异常 user 的流量本身消失，17:05 那一次也在约 30 分钟后自然结束。

影响

  1. 作业 SLA 为 A，19:00-19:30 期间 lag 峰值 179 万，实时状态写出的延迟同步升高。
  2. online 和 offline 两个 Redis 集群的 PC 播放会话状态落后，依赖该状态的推荐侧实时特征受影响。
  3. 单次问题持续 30~40 分钟，重启只能暂时缓解，下一次倾斜出现时仍会复现。

方案设计

核心是给每个 user 在单个窗口内的状态定上限，超出部分直接丢弃。下游本来就按 1024 条截断，丢弃不会改变数据形态。

目标

  1. 单个窗口单个 user 的状态条目有上限，倾斜不再把单 KV 放大到 70 KB 以上。
  2. 不改变上下游数据语义，不改动下游读取方式。
  3. 改动集中在 UDF 内部，不调整 SQL 结构和并行度。

备选方案与取舍

方案作用点预期效果风险结论
窗口条目上限UDF 的 MapView 与 PlayItem直接限制单 KV 上限，倾斜不再放大低，超出部分丢弃采用
两阶段聚合补 merge() 并开启 TWO_PHASE减少 shuffle 和 global 端写回次数中，状态多一份，热点 key 仍集中可选
key 加盐SQL 增加一级聚合真正打散热点 key高，需要改 SQL 并影响下游后续评估

两阶段聚合要求 AggregateFunction 实现 merge()。当前 UDAF 没有实现，planner 因此一直按单阶段执行。即使补上，热点 user 的数据最终仍会哈希到同一个 subtask，收益来自减少 shuffle 和 global 端写回次数，倾斜本身不会消失。

加盐能真正分散热点，但要改 SQL 结构，并确认下游能否接受多一级聚合。这条留作倾斜继续增长时的下一步。

WindowPlaySessionAgg.java限制每窗口条目数
protected static class PlayAggAccum {
    private static final int MAX_ITEMS = 64;

    public void addPlayCid(long clientTime, long avid, long cid, int playedTime,
                           String from_spmid, RecsysAvbasicBody avbasicBody) {
        try {
            Tuple2<Long, String> key = new Tuple2<>(avid, from_spmid);
            PlayItem item;
            if (PLAY_MAP.contains(key)) {
                item = PLAY_MAP.get(key);
            } else {
                if (PLAY_MAP.getMap().size() >= MAX_ITEMS) {
                    return;
                }
                item = new PlayItem(clientTime, avid, from_spmid, avbasicBody);
                PLAY_MAP.put(key, item);
            }
            item.addPlayCid(cid, playedTime, clientTime);
        } catch (Exception e) {}
    }
}
PlayItem.java限制每个视频的 cid 数
private static final int MAX_CIDS = 32;

public void addPlayCid(long cid, int playedTime, long clientTime) {
    if (clientTime < this.clientTime) {
        this.clientTime = clientTime;
    }
    long lastPlayDur = playCids.getOrDefault(cid, 0);
    if (playedTime > lastPlayDur) {
        if (lastPlayDur == 0 && playCids.size() >= MAX_CIDS) {
            return;
        }
        playCids.put(cid, playedTime);
    }
}

两个上限同时加入，先观察哪一侧在丢弃，再决定收紧哪个。上限值是初始经验值，需要按丢弃量调整。

限制与注意事项

上限是业务取舍，超出的播放行为会丢失；倾斜本身没有消除，只是被限制在可控范围内。

数据取舍

丢弃的条目在正常用户身上不会出现，受影响的是异常上报的数据。上限值需要和业务方确认，先按 64 / 32 运行并观察丢弃计数。

根因仍在

本次改动只限制单窗口状态大小。产生倾斜的 user_id 仍会持续出现，数据侧如果能定位到具体的 buvid 或上报来源，应同步治理。

推测数据

value 大小（20~63 KB，正常 ≤2.4 KB）是从 checkpoint 状态文件直接读出的实测值；条目数（8~28 个）仍按指标口径折算，没有把 PLAY_MAP 反序列化出来数过。发出去时建议按这个区分说明。
